## A correction to the earlier framing

The S2 close-out said the `vocals-hq` measurement "makes M3 more valuable", implying research
verdict **R2** (HT-Demucs FT ONNX, ~1.31× faster on CPU) would speed it up. **It would not.**
The backends do not overlap:

| Backend | Presets | R2 applies? |
|---|---|---|
| `audio-separator` (MDXC / RoFormer, MDX-Net, VR) | `karaoke`, `vocals-hq`, `full-vocals`, **`full-vocals-hq`** | **No** |
| `demucs` | `4stem`, `6stem` | Yes |

The 26-minute preset is on the **audio-separator** side. R2 accelerates the demucs side. Both are
worth doing; they are separate pieces of work and must not be conflated again.

## The finding that reshapes this milestone

**Both adapters pass zero tuning parameters.** Everything runs at library defaults:

- `toolshop/stem_extractor_adapter.py` constructs `Separator(...)` with no `mdxc_params`, so RoFormer
  runs at `segment_size=256, batch_size=1, overlap=8`.
- `toolshop/demucs_adapter.py` constructs `demucs.api.Separator(model=…, device=…)` with no `jobs`,
  so it runs at `jobs=0` on an **8-core** machine.

That means the honest first question is not "which faster model should we adopt" but **"how much of
the 9.14× is simply untuned defaults?"** Adopting a new model to paper over unconfigured parameters
would be the wrong order of work, and would bake a second dependency into the lane for a win we may
already have for free.

**So: measure the free levers first, adopt second.** R2 stays on the table and is re-evaluated in
Task 4 against whatever the tuned baseline turns out to be.

## Method

Sweeps run on a **30-second clip** (`ffmpeg`-cut from a real track), not a full song — at 9.14×
realtime a full-track sweep would cost hours and tell us the same ranking.

**Speed alone is not the deliverable.** Each variant's stems are correlated against the baseline
variant's, so a configuration that is faster because it is doing less work shows up as a correlation
drop rather than a win. That comparison is the minimal seed of the eval harness M3 has always wanted
(roadmap: "needs museval eval-harness seed first") — deliberately small, but it is the difference
between a benchmark and a benchmark you can trust.

Winning settings are then validated on the **full 2.85-min track** against the 26.06 min baseline
already on record.

## Tasks

### Task 1 — Measure the free levers · *sweep script written*

`scratchpad/m3/sweep.py`.

**demucs:** `jobs=0` (current) vs `jobs=4`.
**audio-separator RoFormer:** defaults vs `batch_size=4` vs `batch_size=4, overlap=2`.

**Exit evidence:** wall-clock per variant and the per-stem correlation table.

### Task 2 — Decide from the numbers, not the hope

For each backend pick the fastest configuration whose correlation against baseline stays effectively
1.0. **If a variant is faster but measurably different, it is not a free win** — record it as a
quality/speed trade for the user to decide, do not silently adopt it.

**A null result is a real result.** If the defaults are already optimal, say so plainly and move
straight to Task 4; do not manufacture a change to justify the session.

### Task 3 — Wire the chosen settings into the adapters

Both adapters must expose the tuning rather than hardcode it: parameters with the measured values as
defaults, overridable per call. Record the measured figures in `stem_models.py` next to
`cpu_min_per_track`, alongside the machine they were measured on — these numbers are hardware-specific
and will be wrong on the other fleet machines.

Tests: the adapters pass the parameters through (fast, no model execution).

### Task 4 — Re-evaluate R2 against the tuned baseline

Only now is the ONNX question well-posed. If `jobs` tuning already recovers more than 1.31× on the
demucs presets, the ONNX export buys little and adds a dependency and a conversion step — that is a
legitimate reason to defer it, and the tuned numbers are the evidence.

**[USER DECISION]** if adoption still looks worthwhile.

### Task 5 — Full-track validation

Re-run `vocals-hq` end-to-end with the chosen settings and compare against the **26.06 min / 9.14×**
baseline. Update `cpu_min_per_track`. State plainly whether HQ separation is now interactive
(<15 min/track) or still overnight — that is the question the milestone exists to answer.

## Risks

| Risk | Handling |
|---|---|
| `jobs=4` oversubscribes (each worker spawns torch threads on 8 cores) | That is exactly what the measurement is for. If it is slower, record it — a negative result is worth having on record so nobody retries it. |
| Lower `overlap` degrades separation subtly | The correlation check is there to catch it. If it drops, it is a trade, not a win. |
| Numbers are hardware-specific | Record the machine alongside every figure; the fleet (G5) has different CPUs. |
