## Decision Log

### Decision 1: Share engine helpers across CLI and API — never fork semantics

`star_text`, `scan_text`, `vs_star_phrase`, `gauge_level`, `cast_votes(list_id)`
were added to the engine modules with the existing CLI entry points refactored
to delegate to the same core, rather than writing API-only variants.

**Alternatives rejected:**
- API-local reimplementation of star/used/vote logic — would silently drift
  from CLI behavior (e.g. the `(n=…)` low-confidence suffix, the allit-skip in
  vs★ comparison, tag-merge ordering).
- Python-level monkeypatching or thin wrappers that re-parse CLI output —
  fragile, and `cast_votes` needed a new atomic exact-list path anyway.

**Rationale**: the spec's hard rule was "CLI behavior must stay identical."
Delegation makes that structural instead of tested-around: the CLI cannot
diverge because it calls the same function. Verified by the full suite staying
green (244/244) with zero changes to existing test expectations.

*Evidence*: `mairina/fingerprint.py` (+86), `votes.cast_votes` signature,
`cli._cmd_xray` now calls `fingerprint.vs_star_phrase`.

### Decision 2: `draft_id` → `"draft:<id>"` pseudo-filename in the `file` column

The browser-stable draft id is prefixed and stored verbatim in the existing
`stars.file`/`used.file` column; the same column already keys star identity
for the file-based CLI path.

**Alternatives rejected:**
- New `draft_id` column — schema migration for zero behavioral gain.
- Hashing the id — loses debuggability (`SELECT … WHERE file LIKE 'draft:%'`
  is legible in `mt stars` debugging).
- Treating `draft_id` as optional-but-pathlike — rejected absolutely; any
  shape where a client-supplied string reaches `open()` is the failure mode
  this feature exists to avoid.

**Rationale**: "never used as a path" becomes structural — after the prefix,
no code path can resolve it to a filesystem location. Zero schema change,
identity semantics identical to the CLI's file-keyed star.

*Evidence*: `fingerprint.draft_key`; test asserts `file = "draft:../../evil/../../x"`
stored verbatim for a traversal-shaped id.

### Decision 3: Lenient nulls, strict enums — two-tier validation

`None`/missing/`""` on optional fields fall back to defaults (UI sends `null`
for every unset field); invalid enum values, out-of-range numbers, wrong types
→ 400. Empty string is *not* an error where the field is optional.

**Alternatives rejected:**
- Strict-empty (400 on `""`) — would 400 the UI's own request shape; `api.ts`
  emits `null` and occasionally `""`-shaped optionals.
- Lenient-everything (coerce invalid values to defaults) — hides client bugs
  like `lane:"dril"`.

**Rationale**: match the wire format exactly (nulls tolerated), punish only
values that would corrupt semantics (bad enums/ranges). The one test flip of
the session was here: `scheme:""` correctly defaults to AABB — my initial test
wrongly asserted 400.

*Evidence*: `api._lane/_section/_mode/_scheme` null-default pattern;
`test_anchors_validation_and_empty_result`.

### Decision 4: Corpus failure degrades per-route (503), not per-app

`create_app` captures `DbUnavailable`/`CorpusNotAnnotated` at factory time and
stores the exception; corpus-dependent routes return 503 `{"error"}`, while
`stars`/`star`/`used`/`me`/`stats`/`hint-vote`/`vote` keep working.

**Alternatives rejected:**
- Refuse to boot — the spec explicitly requires "the app still starts"; also
  the CLI already degrades (star works without the corpus).
- Global 503 middleware — simpler, but wrongly takes down the app-state routes
  that need only `mairina.db`.

**Rationale**: star/used/me read only `mairina.db`; gating them on corpus
health would break saving drafts on a corpus-less machine for no reason. The
split mirrors the CLI's own degradation boundary.

*Evidence*: `test_corpus_down_app_still_serves` (503 on atlas/xray/anchors,
200 on stats/star); `test_missing_db_still_serves_state_routes`.

### Decision 5: Stale-but-existing `list_id` is votable; unknown → 404

`cast_votes(list_id=<n>)` validates existence inside the vote transaction and
accepts any logged list — not just the latest.

**Alternatives rejected:**
- Latest-only enforcement (reject stale lists) — the whole point of targeted
  voting is that the UI votes on the list it *rendered*; a newer request
  landing mid-review must not orphan the user's clicks.
- Update-or-skip stale votes — silently wrong attribution.

**Rationale**: "unknown/stale → 4xx" in the spec meant *unknown* ids; a real
list that merely aged is still the correct vote target. Atomic validation +
insertion in one transaction prevents a TOCTOU where the list disappears
between check and write.

*Evidence*: `test_vote_targets_the_exact_list` — votes lid1 after lid2 logged,
200; lid 99999 → 404.

### Decision 6: Contract keys never shrink — `null` is a first-class value

`vs_star`, `assonance`, `target` are always present; when nothing fires they
are `null`, not omitted. `NoAnchors` → `items: []` + logged `list_id` (200).

**Alternatives rejected:**
- Omitting empty keys — breaks the frozen TypeScript interfaces and makes the
  client check `in` instead of truthiness.
- 4xx on `NoAnchors` — an empty result shelf is a legitimate find; returning
  an error would force the UI to distinguish "no anchors" from "bad request"
  off the error string.

**Rationale**: the contract is frozen and the UI is being built in parallel;
the cheapest correctness guarantee is that the response schema is a constant,
with `null`/empty carrying the "nothing found" signal.

*Evidence*: `test_xray_happy_and_exact_shape` asserts `vs_star is None` and
`target is None` keys present; `test_anchors_validation_and_empty_result`.
